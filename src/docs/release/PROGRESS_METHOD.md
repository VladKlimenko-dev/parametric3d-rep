# Как считается выполнение (с 2026-10-09)

До 2026-10-09 в отчётах давались две оценки — «близость к промышленному ядру» и «выполнение шагов инструкции» — без
перечня, из которого они следуют. Они были экспертными, их рост на 1% за шаг ничем не подтверждался. Заменены тремя
числами, которые считает `tools/progress_score.py` из `PROGRESS_ITEMS.tsv`; у каждой строки — статус и доказательство.

## Три числа

1. **Выполнение инструкции.** 125 требований шагов KRN-00…KRN-11 (пункты «Сделать», процедуры и «Приёмка» каждого шага).
   Статус: 1 — сделано и проверяется (названа проверка); 0.5 — сделано для части области (названа часть); 0 — нет или «не
   проверено». Два значения: по пунктам (каждое требование равноценно) и с весами трудоёмкости шагов. Веса зафиксированы
   до подсчёта: KRN-00 2, 01 5, 02 6, 03 8, 04 10, 05 10, 06 18, 07 18, 08 8, 09 7, 10 5, 11 3 (сумма 100). Прямой построитель
   сопряжений и завершение операций — самые тяжёлые шаги, поэтому у них наибольший вес.
2. **Покрытие обязательной матрицы возможностей** (11 групп из инструкции; внутри группы — строки матрицы). Принятый путь
   корпуса — 1, частично — 0.5, обход (резцы с перекрытием и т. п.) — 0.25, нет / не проверено — 0. Это доля функций,
   у которых есть путь, а НЕ промышленная готовность: «принято (корпус)» ещё не прошло квалификацию KRN-11.
3. **Ворота промышленного выпуска** — 15 пунктов чек-листа инструкции, только «закрыт / не закрыт». Инструкция
   определяет «100% промышленной готовности» именно так и запрещает заменять это общей оценкой.

## Почему прежние числа расходились

«Близость» (≈59%) включала возможности, которые были в r54 до начала программы (2.5D-булева, выдавливание, отверстия,
многогранное ядро), и оценивалась на глаз; при подсчёте по строкам матрицы получается 38%. «Выполнение» (≈24%) по
перечню — 21.4% с весами и 28.0% по пунктам.

Следствие для работы: поставка, которая не меняет статус ни одного требования, — исправление дефектов, и это нужно
называть прямо. Требование переходит в 1 только с проверкой, и строки с 0.5 не повышаются без новой проверки области.

Правило 2026-10-11 (судья не всегда прав): расхождение с OpenCascade без решения Монте-Карло («occt-wrong?») разбирается
независимой проверкой — Монте-Карло по точным классификаторам исходных операндов с достаточным числом точек (`DIFFMC`);
вердикт — только при расхождении ≥ 5σ одной из сторон. Серия 8, случай 42: OpenCascade в 5.1σ, мы в 0.6σ.

перечень `FREEFORM_STAGE.md`. Отчёт после каждой поставки заканчивается строкой «ворота N/15»; при 15/15 — напоминание
пользователю, что можно переходить к этапу FF (начинать только по его распоряжению).
